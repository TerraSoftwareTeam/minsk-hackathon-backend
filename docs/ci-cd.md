# CI/CD

## Зачем

Любое изменение в коде попадает на прод автоматически, и только после того, как пройдёт проверки. Вручную на сервер никто не заходит и ничего не копирует.

Что это даёт команде:

- **Скорость.** От коммита до работающего прода проходят минуты, без участия человека.
- **Надёжность.** Код, который не собирается или ломает тесты, до прода не дойдёт.
- **Воспроизводимость.** Прод всегда собирается одинаково, из того, что лежит в `main`. Ситуация «у меня локально работает» исключена.

## Как это устроено

```
Разработчик ──push──▶ GitHub (ветка main)
                         │
                         ▼
               ┌──────────────────────┐
               │ 1. Проверка (CI)     │  облако GitHub
               │  сборка + тесты      │
               └──────────┬───────────┘
                     ✗ ошибка → стоп, прод не трогаем
                     ✓ успех
                          ▼
               ┌──────────────────────┐
               │ 2. Доставка (CD)     │  наш сервер
               │  новая версия кода   │
               │  пересборка Docker   │
               │  перезапуск сервисов │
               └──────────┬───────────┘
                          ▼
               ┌──────────────────────┐
               │ 3. Старт приложения  │
               │  миграции БД         │
               │  healthcheck         │
               └──────────────────────┘
```

### 1. Проверка (CI)

Запускается на каждый push в `main`, на чистой машине GitHub. Там проект собирается с нуля и проходят тесты. Если хоть один шаг упал, пайплайн останавливается, а прод продолжает работать на предыдущей версии.

### 2. Доставка (CD)

На нашем сервере стоит агент GitHub Actions (self-hosted runner). После успешной проверки он:

1. забирает свежий код из `main`;
2. пересобирает Docker-образ приложения;
3. перезапускает контейнеры с новой версией;
4. удаляет старые образы, чтобы они не забивали диск.

Агент сам забирает задачи у GitHub, поэтому серверу не нужно принимать входящие подключения от CI. Хранить SSH-ключи от сервера в GitHub тоже не нужно.

### 3. Старт приложения

- **Порядок запуска.** API стартует только после того, как PostgreSQL и Redis прошли свои проверки готовности.
- **Миграции.** При старте API автоматически приводит схему БД к актуальной версии. Код и структура базы всегда соответствуют друг другу.
- **Healthcheck.** Docker регулярно опрашивает API и следит, что оно отвечает.
- **Автоперезапуск.** Если сервис упал, Docker поднимет его снова.
- **Сохранность данных.** Данные PostgreSQL и Redis хранятся в отдельных томах и не теряются при пересборке и перезапуске.

## Дополнительные гарантии

- **Деплои не накладываются друг на друга.** Если несколько push пришли подряд, они выполняются по очереди, а не параллельно.
- **Полноценный прод-образ.** Сборка идёт в два этапа: в итоговый образ попадают только собранное приложение и зависимости, нужные в рантайме. Инструменты разработки туда не попадают.
- **Без root.** Приложение в контейнере работает от непривилегированного пользователя.
- **Изоляция.** Наружу открыт только nginx. API, БД и Redis доступны лишь внутри сервера.
